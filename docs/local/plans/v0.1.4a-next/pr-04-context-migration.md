## Objective and exit boundary

## Baseline / current architecture constraints

The current source confirms a broad persistence and orchestration seam; the ownership matrix below is a review input, not proof every proposed move is already safe.

### Verified source baseline

- `internal/agentstate` owns `SQLiteStore.open`, schema setup and the ordered schema migrations. `SQLiteStore` opens one operational database and initializes all registered context tables on access. `NewIdentityStore` and `NewEnrollmentStore` are compatibility constructors over that same store.
- Identity SQL implements `identity.InstallationIdentityRepository`; initialization is a transaction that validates and stores one UUID, then returns the committed value. Enrollment SQL implements `enrollment.AttemptRepository`; SQLite contains request/result metadata and protected-store references, while credential values are passed to the credential-store adapter, not persisted here.
- Enrollment operations have observable recovery semantics: a lost response remains a durable pending attempt; explicit re-enrollment retains prior binding metadata and credential references; retired credential references are cleared only after protected-store deletion succeeds. `CompleteAttempt` commits the validated Core result and protected credential reference atomically.
- `internal/agentstate/sqlite_approval.go` owns the cross-table approval transaction. It validates proposal and inventory revisions, desired-state CAS, uniqueness, then writes desired Integration state and the approved proposal together. `internal/agentstate/sqlite_materialization.go` similarly applies revision-bound Template projections transactionally. Moving either half independently would break atomicity.
- `internal/reconciliation` imports `internal/agentlifecycle` for the clean-baseline and candidate-apply DTOs, and imports `internal/agentstate` for durable attempt/error and candidate-outcome types. `agentlifecycle.ApplyCollectorCandidate` validates generation/fingerprint/digest and delegates activation through the lifecycle coordinator. Runtime activation journaling and Agent-state updates are coupled.
- The supported workflow uses the Windows worktree branch `feat/v0.1.4a-next-work`. At the start of this slice, the only worktree artifact was the preserved untracked zero-byte `cmd/agentctl/otel.yaml.lifecycle.lock`; the current implementation diff is limited to the identity adapter, its compatibility seam/test, and this plan/progress record. `docs/shared/` remains untouched. A submodule status command could not read Git's Windows named-pipe/session object in this shell; parent status with submodules ignored shows no shared gitlink modification.

### PR-04c inventory/proposal adapter contracts (source audit complete before code)

- **Inventory snapshot:** `InventoryRepository.Snapshot` returns material revision, independent write revision, deterministically ordered resources and provider status from one read transaction. `CommitProviderSnapshot` accepts only a complete normalized provider snapshot, replaces only that provider instance's rows atomically, increments write revision for every successful write, and increments material revision only when the caller reports a material change. The expected write revision is a CAS token; stale writes return `discovery.ErrSnapshotConflict`.
- **Inventory failure:** `RecordProviderFailure` requires bounded provider identity and a safe error code, updates provider attempt/error status and write revision, and preserves prior successful timestamp, resource count, resource records, and material revision. This write also invalidates stale snapshot CAS tokens.
- **Proposal persistence:** `ProposalSnapshot` returns stable ID order from one read transaction and validates the persisted payload against indexed identity/status/revision columns. `PutProposal` validates payload bounds and the one-step revision transition, then inserts or updates by expected revision; conflicting writers return `discovery.ErrProposalConflict`. `DismissProposal` is revision-bound and only accepts the existing legal pending/needs-input transition. `ProposalManager.Refresh` is called only with one complete deterministic matching evaluation; only that successful pass may mark absent proposals stale. Existing approved/dismissed idempotency and material-change behavior remain in `internal/discovery`.
- **Shared storage boundary:** inventory and proposal adapters use the existing `SQLiteStore.OpenDatabase` and the same in-process `sqliteUpdateMutex` as approval, materialization, and Agent-state writes. Their migrations remain versions 10, 11, and 12 under `agentstate`; this slice adds no schema or migration change. Compatibility constructors on `SQLiteStore` remain while runtime and CLI callers migrate.
- **Approval transaction:** `ApprovalService` reads the proposal and verifies current candidate evidence before calling `ApprovalRepository.CommitApproval`. `agentstate` performs proposal revision, candidate digest, inventory write revision, desired revision, uniqueness, and approved-instance checks, then writes the approved instance, desired revision, and proposal status in one SQLite transaction. `alreadyApproved` remains idempotent. Extracting the proposal repository must not relocate or split this cross-context atomic operation.
- **Composition:** runtime/CLI callers currently obtain both repositories from `agentstate.SQLiteStore`; the adapter extraction changes the constructor target only. No CLI output, command, inventory evidence, proposal state transition, matching policy, or approval behavior is in scope.

### PR-04d Configuration persistence contracts (source audit complete before code)

- **Desired Integration repository:** `Put` validates a resolved non-Template-owned instance, compares its item revision, and atomically updates the item plus desired-set revision. Identical intent is a no-op that preserves both revisions. `Delete` rejects Template-owned instances, remains idempotent for missing IDs, and advances the desired-set revision only when a row is deleted. `Snapshot` returns sorted instances and the set revision from one read transaction. The `IntegrationInstance` model remains owned by `integration`; this migration does not move it.
- **Template repository:** only local Templates are writable; updates use per-Template CAS, immutable Definition ID, permanent deleted tombstones, bounded validated JSON, and a set revision that advances only for material changes. No-op writes keep the prior Template item/set revisions. Snapshots include tombstones in stable ID order and read the set token consistently. Migration version 13 and its table shape remain unchanged.
- **Materialization transaction:** `ApplyTemplateProjection` compares inventory write, Template set, and desired-set tokens in one transaction; verifies Template ownership/revision and generated resource bindings; applies all upserts/suspensions; and advances desired revision only if projection changed. The optional desired-configuration event is published after commit; a dropped wakeup does not roll back durable state. This operation must move as one unit because it spans Discovery inventory, Configuration Templates, and desired Integration rows.
- **Approval transaction:** proposal revision/status/digest, inventory write token, desired-set token, binding uniqueness, and instance revision are checked before the repository writes the approved Integration and proposal outcome in one transaction. Repeated approval returns the committed instance without applying another mutation. Candidate revalidation stays in `ApprovalService`; the transaction stays in the persistence adapter. This operation must move as one unit.
- **Storage and side effects:** all Configuration adapters receive `SQLiteStore.OpenDatabase` and the shared SQLite write mutex. Schema ownership/order stays under `agentstate` (desired state migration 6; Template migration 13); this migration adds no schema version. Event publication is post-commit and advisory. Preserve existing command/service facades until runtime and CLI callers are migrated.
- **Candidate-state boundary:** `agentstate` candidate outcome persistence still reads the desired-set revision through its own narrow SQLite helper. PR-04e keeps this adapter and its journal/recovery transaction unchanged while relocating the consumer-facing apply and baseline DTOs.
- **Implementation boundary:** migrate all four repositories into one `internal/configuration/sqlite` adapter package in one reviewable slice. The materialization adapter shares the desired-set and Template revision readers with the standalone repositories, and both cross-context write operations share the same database and write lock. Each approval/materialization operation remains one transaction. Keep all four constructors available through `agentstate.SQLiteStore`; do not move the `IntegrationInstance` domain model or invent new transaction/provider abstractions.

### PR-04e Runtime apply-port inversion (contract decision before code)

**Target decision:** `reconciliation` owns the consumer-facing `CandidateApplier` and `BaselineReader` contracts, including their request/result and baseline snapshot DTOs. Runtime behavior remains in `agentlifecycle`; the thin `cmd/agentctl` composition adapters implement the consumer ports and map the runtime baseline snapshot to the reconciliation-owned snapshot. This follows the architecture rule that ports belong to their consumers while Runtime owns activation, readiness, journal, and LKG behavior. It removes reconciliation's concrete dependency on lifecycle code without moving runtime behavior into reconciliation.

**Source evidence:** `reconciliation.Controller` currently imports `agentlifecycle` only for `CleanBaselineSnapshot`, `CandidateApplyRequest`, and `CandidateActivationOutcome`. `cmd/agentctl/reconciliation_runtime.go` already provides baseline and applier adapters. `agentlifecycle.ApplyCollectorCandidate` and `configurationCoordinator.ApplyCandidate` own freshness checks, activation locks, SQLite admission, generation transitions, readiness, failure journaling, and LKG recovery. `collectorruntime.Candidate` is an immutable value produced by the existing compiler and remains the candidate contract; do not duplicate its bytes/digest/artifact metadata in a second DTO. `agenthealth` already owns transient observation evaluation and local status adapters, so no health package move is justified by the current source.

**Contract:** `BaselineReader.Snapshot() (BaselineSnapshot, error)` returns a deterministic clean render input with its observed desired generation and fingerprint; the current reader does not promise a cross-store read transaction. `CandidateApplier.ApplyCandidate(context.Context, CandidateApplyRequest) (CandidateActivationOutcome, error)` receives the complete immutable candidate plus desired Integration revision, expected M2 generation, and baseline fingerprint. Runtime rechecks those revisions and candidate/platform/digest invariants before admission; `AlreadyApplied` is true only for an idempotently confirmed terminal applied generation. A newly admitted candidate is not reported applied until readiness records the terminal mapping. Stale revision/generation/baseline errors remain recognizable by reconciliation; activation and recovery errors remain visible. The call may persist admission/journal state and activate the Collector; validation and stale rejection happen before admission. SQLite state plus activation journal/Gateway update transaction semantics, LKG restoration, recovery artifact ownership, and polling fallback remain unchanged.

**Implementation sequence:** add the consumer contracts under `internal/reconciliation/contracts`; alias the DTOs at the reconciliation package surface; switch `Controller` and its tests to those types; adapt `agentlifecycle` as the runtime implementation; map `CleanBaselineSnapshot` to `BaselineSnapshot` in `cmd/agentctl`; update CLI status helpers and tests to the consumer DTO; enforce the forbidden `reconciliation -> agentlifecycle` import in `scripts/check-architecture.ps1`. No database or service-lifecycle code moves in this slice.

**Ruling:** keep the contract definitions in the leaf package `internal/reconciliation/contracts`, with aliases at the parent package surface. Importing the parent from runtime creates a test-time cycle because same-package reconciliation tests exercise runtime behavior; the leaf package keeps ownership under reconciliation and permits the dependency inversion without changing tests to an external package.

**Scope boundary:** this is an import-direction and contract-location refactor. Do not change CLI output, SQLite schemas/migrations, candidate compilation, retries, Core authority, OpAMP/security policy, Collector configuration, service lifecycle, or health semantics. Do not move `agenthealth`; retain `agentlifecycle.CleanBaselineSnapshot` as the lifecycle baseline builder's return type, and map it to the reconciliation-owned snapshot at the composition boundary. Verification must prove reconciliation no longer imports `agentlifecycle` and preserve existing candidate activation/recovery tests.

## Contract audit ruling and migration order

1. **Ruling:** keep schema migration and database opening under `agentstate` for this slice, and pass its opener into the context-owned identity SQLite adapter. This preserves the single migration order and old database path without adding a generic provider package. Cost if wrong: `agentstate` remains a shared technical infrastructure owner and may need a later provider extraction if other contexts require independent storage composition.
2. Keep approval and Template materialization out of the first adapter extraction: each is a multi-table transaction spanning different domain records and must move as one repository operation.
3. **Superseded by PR-04e:** the earlier ruling deferred the `reconciliation -> agentlifecycle` import inversion pending ownership review. The delegated decision is now to make the port consumer-owned in `reconciliation` and use explicit composition adapters, consistent with the architecture's consumer-owned-port rule. The contract keeps one canonical DTO and the generation, fingerprint, digest, readiness, and LKG semantics. Historical ruling retained to show why this slice was gated. Cost if wrong: a leaf contract package adds one package hop and may need relocation if another bounded context becomes its true owner.
4. **Ruling:** inject the existing `agentstate` SQLite write mutex into the enrollment adapter rather than creating a second lock. This keeps in-process writes serialized across repository values while SQLite immediate transactions and busy timeout continue coordinating other processes. Cost if wrong: sharing one mutex can increase local writer contention, but replacing it requires concurrency evidence and must not admit duplicate attempts.
5. Split PR-04 into separately reviewable slices. Current order: (a) identity SQLite adapter with existing `agentstate` opener/migration owner and compatibility facades; (b) enrollment adapter with protected-store side effects left in the application service; (c) inventory/proposal adapters; (d) all four Configuration repositories as one package while preserving each atomic transaction; (e) candidate/runtime and health ownership only after the apply-port decision. These slices do not change Core or security policy.

## Edge cases and failure semantics

- A partial provider snapshot cannot delete active inventory.
- Two writers cannot bypass CAS or create duplicate approvals.
- Old enrollment lost-response/revocation behavior remains identical.
- No duplicate desired IntegrationInstance types during migration.
- Failed candidate preserves LKG and activation journal atomicity.
- Uninstall cannot remove dependencies not installed by Agent.
