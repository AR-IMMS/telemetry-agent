# PR-09.5 — Architecture Consolidation Implementation Plan

> **For agentic workers:** Use `superpowers:executing-plans` to implement this plan task by task. Preserve sequential checkpoint order: start only after PR-07, PR-08, and PR-09 pass.

**Goal:** Make production source ownership discoverable across the seven bounded contexts while preserving all verified behavior and persisted data.

**Architecture:** Audit the current source first, then migrate ownership in small behavior-preserving slices. Folder layout is a flexible baseline; actual moves follow package contents, imports, transactions, active consumers, and domain ownership. This checkpoint does not transfer Collector lifecycle authority.

**Tech Stack:** Go 1.25.5, existing SQLite database and migration tooling, current Windows/Linux build and E2E harnesses, existing architecture guards.

**Spec:** [Context boundaries](../../architecture/v0.1.4a-next/context-boundaries.md), [source structure](../../architecture/v0.1.4a-next/source-structure.md), [state and event model](../../architecture/v0.1.4a-next/state-and-event-model.md), [acceptance criteria](../../requirements/v0.1.4a-next/acceptance-criteria.md), and this plan's accepted release mission. Reconcile conflicting or stale architecture documents before implementing each slice.

## Global Constraints

- Preserve the seven bounded contexts: Identity, Inventory, Monitoring, Configuration, Runtime, Health, and Operations.
- Application Host and Platform are supporting technical boundaries, not business contexts.
- Keep Domain independent of SQLite, HTTP, Docker, OpAMP implementation, SCM/systemd, and process execution.
- Application use cases depend on domain models and explicit ports; adapters implement those ports.
- Cross-context calls use explicit public contracts; no context imports another context's private persistence.
- Keep one operational SQLite database, existing schema/migration order, WAL/CAS/revision behavior, and cross-table transaction boundaries.
- Preserve CLI commands/flags/output/exit behavior, enrollment/credentials, monitoring profiles, Collector ownership, LKG, and verified recovery behavior.
- Do not combine moves with schema, protocol, CLI, monitoring, runtime, security, or lifecycle-ownership behavior changes.
- Keep PR-05 Observer/Receiver Creator ownership and PR-07 Supervisor ownership exactly as already verified; do not create a second lifecycle engine.
- Keep source files normally around 300–400 lines with justification for larger files, consistent with shared policy; retain the repository's 450-line automated ceiling.
- Preserve all existing worktree changes and submodule state. Do not edit `docs/shared/` or final-release branches.

## Review Focus

- Mixed-purpose packages may contain independent domain ownership; audit symbols and consumers before moving files.
- Cross-table transactions can be broken by package moves that split a single atomic operation; map transaction callers and test rollback/commit behavior.
- Compatibility facades may still have external or CLI consumers; prove no consumers before removal and retain required rollback facades.
- Import-graph checks can pass while business orchestration remains in CLI or composition; inspect workflows and test command behavior.
- Platform build tags, SQLite migrations, and service/process ownership can regress under moves; run native Windows/Linux gates for each affected slice.

## Exit Criteria

- All production packages and domain models have one clear owner.
- The source organization reflects the seven contexts, with any layout deviations justified by actual code.
- CLI contains no business workflows or long-running orchestration; Application Host contains composition/lifecycle wiring only.
- Domain/Application/Infrastructure direction is enforced by architecture checks and contract tests.
- One operational SQLite database, migration compatibility, CAS, and all existing atomic transactions remain intact.
- No behavior, public CLI, external contract, security policy, monitoring policy, dependency ownership, or lifecycle transfer was bundled into the structural change.
- Compatibility facades are removed only when safe or are explicitly justified and tested.
- Previously verified PR-01 through PR-09 behavior passes the full native Windows/Linux regression and relevant E2Es.
- PR-10 verifies the consolidated source and release artifacts.
