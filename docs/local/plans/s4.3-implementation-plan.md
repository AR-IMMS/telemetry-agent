# S4.3 Integration Matching & Configuration Resolution Implementation Plan

> **For agentic workers:** Use the repository's implementation workflow task-by-task. Steps use checkbox syntax for tracking.

**Goal:** Match persisted discovered resources to existing Integration Definitions and return deterministic, validated configuration candidates without mutating desired state or activating Collector.

**Architecture:** Extend the S1 Definition/Registry with optional match metadata and a single active matchable version per Integration ID. A pure Integration matcher consumes a consistent read-only projection of SQLite inventory, uses definition-owned selectors/builders, and receives capability assessment through composition. The Agent CLI exposes read-only diagnostics; S4.4 owns proposals and approval.

**Tech stack:** Go, existing S1 Integration package, S4 Discovery contracts, SQLite JSON inventory, existing S2 capability catalog, existing `agentctl` conventions.

**Spec:** [S4.3 Technical Design](../architecture/s4.3-integration-matching.md); [ADR-0002](../adr/0002-generic-integration-matching.md).

## Global constraints

- Do not add a second Integration Registry or parallel S1 validation/resolver framework.
- Do not make Integration depend on Discovery, SQLite, CLI or Collector Runtime.
- No Desired State writes, proposals, S3 invocation, Collector activation or secret inference.
- Exact repository matching only; no display-name or substring fallback.
- Only an unambiguous explicit loopback host-published endpoint can auto-resolve initially.
- Capability support remains separate from identification and must use selected pinned artifact evidence.
- Freshness decisions use one captured evaluation timestamp per match report; identical snapshot, definitions, capability evidence and timestamp must yield identical statuses and ordering.
- Keep non-test Go files at or below 450 LOC; use existing bounded contexts and package conventions.
- No `device` ResourceKind, device provider, PostgreSQL/MongoDB implementation or Docker event stream in this work.

## Review focus

- Image alias parsing must not merge private registries or mistake Docker ImageID for a registry digest.
- Old SQLite JSON rows must still decode and produce non-actionable results when image evidence is absent.
- A Docker wildcard bind (`0.0.0.0`/`::`) must never become an endpoint candidate.
- Multiple matchable definition versions or multiple matching definitions must not select an arbitrary winner.
- Capability status and candidate digest must not imply reachability, health, activation or delivery.

## Slice 1 — Matchable Inventory Evidence

**Current status:** Implemented in the current checkout; retain as a regression baseline.

**Goal:** Add only the normalized Docker evidence necessary for exact matching while preserving existing inventory records and provider behavior.

**Scope:** Docker image reference, exact normalized repository, optional tag/digest when directly available, Integration-facing projection field needs, JSON compatibility. Exclude device providers and broad Docker refactoring.

**Implemented source/test touchpoints:**

- `internal/discovery/docker/provider.go` maps `container.Summary.Image` to bounded raw and normalized evidence.
- `internal/discovery/docker/provider_test.go` covers raw reference, private registry, malformed reference and explicit digest behavior.
- `internal/agentstate/sqlite_inventory_test.go` and discovery persistence tests cover additive inventory JSON behavior; no SQL migration was needed.

**Dependencies:** Existing Moby client and discovery normalizer; no new SQL schema or Integration runtime dependency.

**Implementation sequence:**

1. Add failing Docker mapper tests for exact raw image reference, repository, tag and optional digest; include private registry and malformed/overlong inputs.
2. Add failing normalizer tests for accepted image field bounds and rejection of secret-like or malformed attributes.
3. Implement conservative parser/mapping using an already pinned parser if suitable; keep ImageID separate and never label it as a registry digest.
4. Preserve image attributes through complete-snapshot normalization and SQLite JSON persistence.
5. Add populated pre-change JSON payload and SQLite restart tests proving missing image fields decode without migration or data loss.
6. Run `gofmt`; `go test ./internal/discovery/... ./internal/agentstate -count=1`; `go vet ./...`; `go build -buildvcs=false ./...`; and diff/LOC checks on Windows and Linux CI.

**Acceptance criteria:** Existing records remain readable; exact image repo and original reference survive a restart; arbitrary labels/environment are not copied; unknown image forms do not receive a guessed repository; no unrelated endpoint semantics change.

**Risks / rollback:** Parser normalization can create false equivalence. If canonicalization cannot be proven conservative, preserve the original reference and only produce repository values for known valid forms; matcher returns no match otherwise. Changes are additive JSON and can be rolled back without a database downgrade.

**Suggested commit boundary:** `feat(discovery): persist bounded Docker image evidence`.

## Slice 2 — Generic Matcher & Redis Definition

**Current status:** Implemented in the current checkout; retain as the S4.3 contract baseline.

**Goal:** Implement deterministic matching, candidate validation, endpoint resolution, ambiguity reporting and capability compatibility without persistence or runtime effects.

**Implemented source/test touchpoints:**

- `internal/integration/integration.go`, `registry.go`, `matching.go`, `matching_engine.go` and supporting matching files implement optional metadata, stable enumeration, deterministic matching and immutable candidates.
- `internal/integration/redis/definition.go` implements the exact repository selector and pure endpoint candidate builder using existing Redis validation.
- `internal/integration/*_test.go` and `internal/integration/redis/*_test.go` cover Registry, deterministic results, capabilities, endpoints, validation and defensive copies.

**Dependencies:** Slice 1 image evidence. Capability assessment is an injected Integration-owned read-only contract; the S2 Catalog remains authoritative.

**Implementation sequence:**

1. Add failing contract tests for optional matching definitions, no-match definitions, stable enumeration and rejection of two matchable versions for one ID.
2. Add failing matcher tests for exact selector evaluation, stable evidence/result ordering, unknown kinds, stale/missing resources and ambiguous definitions.
3. Add failing candidate tests for immutable canonical bytes, resource fingerprint exclusions (`LastSeenAt`, global revision), candidate digest stability, changed endpoint/definition inputs and freshness status changing only when the captured `AsOf` crosses the stale threshold.
4. Implement pure orchestration and result status axes; invoke existing Definition validation on candidate settings without creating a desired Integration instance or calling S1 `Resolver.Resolve`.
5. Implement Redis matching with exact normalized repository evidence and conservative endpoint selection; wildcard/private/ambiguous endpoints return `needs_input`.
6. Add capability assessment through the narrow read-only port; prove `supported`, `unsupported`, `unverified` and `not_assessed` remain separate from match status.
7. Run `go test ./internal/integration/... -count=1`, `go vet ./...`, `go build -buildvcs=false ./...`, `go test ./...` in CI on both Windows and Linux, and non-test LOC checks.

**Acceptance criteria:** Generic engine has no technology-specific branches; unchanged inputs yield identical candidates/results; validation and secret checks fail closed; unsupported capability is visible and S4.4 treats it as non-actionable by default; definitions without match metadata still resolve manually configured instances.

**Risks / rollback:** Registry metadata may affect construction sites. Keep it optional and validate all existing constructors. If capability identity cannot be exposed safely from Catalog, report `unverified` until composition can prove selected artifact evidence; do not infer support.

**Suggested commit boundary:** `feat(integration): add generic resource matching`; keep Registry/type changes and engine changes together if splitting would leave a non-buildable intermediate commit.

## Slice 3 — Composition, Diagnostics & Live E2E

**Current status:** Implemented in this checkout. The live Windows matching path is verified; Linux runtime telemetry delivery remains open.

**Goal:** Prove actual Docker inventory flows through the matcher and produce candidates/read-only diagnostics without changing desired or runtime state.

**Files/packages:**

- Existing `cmd/agentctl/integration_matching.go` obtains one SQLite snapshot, maps it into the Integration projection, assesses the selected catalog and renders read-only diagnostics; `cmd/agentctl/integration_command.go` dispatches `integration match`.
- Existing `cmd/agentctl/integration_matching_test.go` covers persisted fixture output and verifies no Desired State mutation.
- `cmd/agentctl/discovery_live_e2e_test.go` contains an opt-in live Docker test that invokes `agentctl integration match` against fresh SQLite inventory before explicit S4.4 approval. Keep its read-only assertions distinct from the downstream approval/activation assertions.

**Dependencies:** Slice 2 contracts; opt-in Docker endpoint; disposable Docker Redis fixture and platform-specific permissions for live execution.

**Implementation sequence:**

1. Verify the one-snapshot projection, deterministic output, safe diagnostics and no-write assertions.
2. Verify capability assessment comes from the selected static catalog and platform artifact evidence; unsupported/unverified results remain visible and non-actionable by default.
3. Verify the production Registry still resolves manual instances and exposes one matchable Redis version, independent of platform capability assessment.
4. Run the opt-in disposable Docker Redis test: provider discovery commits to isolated SQLite, then the read-only command returns a candidate or `needs_input` output.
5. Prove the fixture's local Docker endpoint and Agent host context before treating loopback as actionable; if the context cannot be established, assert `needs_input` and no candidate.
6. Assert live matching leaves Desired Integration revision, S3 outcome state, M2 generations and Collector configuration unchanged before approval begins.
7. Run `go test ./cmd/agentctl -count=1`, `go test ./... -count=1`, `go vet ./...`, `go build -buildvcs=false ./...` and Windows/Linux CI; run live Docker E2E only on provisioned runners and report skips separately. Cross-compilation alone is not platform execution evidence.

**Acceptance criteria:** Actual Docker resource data reaches the read-only matcher through SQLite; output includes identity, evidence, exact definition version, independent status axes, fingerprint/digest and capability assessment; the verified local Windows Docker context may yield a loopback candidate, while unverified contexts fail closed; no S4.3 CLI or composition path writes Desired State or calls S3/M2.

**Risks / rollback:** Live Docker tests require privileged local socket/named-pipe access; keep opt-in environment gating and isolated temp SQLite. The Windows local named-pipe test establishes context only for that tested setup. Other providers/endpoints and Linux runtime delivery remain unverified; fail closed or require input there. If a platform lacks Docker, mark only the live test skipped while running portable tests on that platform; cross-compilation alone is not platform execution evidence.

**Suggested commit boundary:** `feat(agentctl): expose read-only integration matches` plus a separate E2E test commit if independently reviewable.

## Cross-slice handoff and completion

Slice 1 provides exact normalized evidence. Slice 2 consumes an Integration-owned snapshot contract and emits immutable candidates plus capability evidence. Slice 3 composes those contracts and remains responsible for proving the end-to-end read-only path. S4.4 consumes match identity, resource fingerprint, candidate digest and capability evidence, but must re-read inventory and re-match before approval and Configuration CAS.

S4.3 Definition of Done: all three slices meet their acceptance criteria; existing S1 instance resolution, S2 compilation, S3 reconciliation, M2 lifecycle, enrollment, host monitoring and existing inventory records remain compatible; Windows/Linux portable checks pass; live Docker limitations are accurately reported; no proposal, Desired State write, activation or Collector health claim is introduced.
