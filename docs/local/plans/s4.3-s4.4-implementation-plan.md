# S4.3 + S4.4 Integration Matching and Approval — Execution Plan

> **For agentic workers:** Use the existing implementation workflow task-by-task. Keep each task independently testable and commit coherent changes as they become reviewable.

**Goal:** Convert discovered resources into durable, explicitly approved Integration desired state and let the existing Agent Service/S3/S2/M2 workflow activate it.

**Architecture:** S4.3 adds deterministic Integration-owned matching over a read-only inventory projection. S4.4 stores proposals in Discovery/Inventory and performs approval in Configuration through one short SQLite transaction that commits the desired instance, desired-set revision and proposal outcome together. Existing S3/M2 remain the only convergence and activation path.

**Tech stack:** Go, existing Moby v0.6.2 client, SQLite WAL and migrations, existing Integration Registry/Resolver, S2 capability catalog, existing Agent Service and `agentctl` conventions.

**Specs:** [S4.3 technical design](../architecture/s4.3-integration-matching.md), [ADR-0002](../adr/0002-generic-integration-matching.md), [S4.4 technical design](../architecture/s4.4-monitoring-proposal-approval-design.md), [S4.3 three-slice plan](s4.3-implementation-plan.md).

- Provider failure already preserves resources and last-success evidence. The existing test asserts this; do not duplicate it.
- Material inventory revision does not advance on non-material writes, so it is not a sufficient writer CAS token. Add a distinct write revision in migration 11; keep material revision semantics unchanged.
- Additive S1 source/binding fields remain provider-neutral JSON values. Credentialed proposals remain non-approvable until an approved secret-reference and Collector expansion contract exists.
- Do not change Target Architecture or `docs/shared` unless a code-proven contradiction requires a reviewed update.

## Global constraints

- Preserve PR #17 worktree content; stage explicit paths only. The existing CRLF/LF status noise is semantically empty and must not be normalized in unrelated source files.
- No Integration-specific branches in generic matching, S3 or M2; no second registry, scheduler, event bus or activation path.
- Inventory evidence and proposal diagnostics are bounded, allowlisted and secret-free.
- Never hold a SQLite transaction during Docker, matching, capability assessment or external validation.
- Approval is explicit, revalidates latest evidence and CAS-checks proposal, inventory writer token and desired-set revision.
- Every new non-test Go file remains at or below 450 LOC; use GoDoc for every package and exported API.
- Use temporary state databases and uniquely named fixtures. Never prune Docker or affect unrelated containers/databases.

## Review focus

- Non-material inventory updates must invalidate a stale writer without incrementing the material revision.
- Image normalization must retain private-registry identity and never reinterpret Docker ImageID as a registry digest.
- Matcher freshness changes with its single captured `AsOf`, while stable resource fingerprints exclude poll times/global revisions.
- Proposal identity is provider-scoped and stable across definition revisions; proposal refresh and approval have distinct CAS boundaries.
- Concurrent approvals and restart recovery must never produce an approved proposal without its desired instance or duplicate desired instances.
- Collector readiness is not proof of Redis telemetry delivery; only observed Redis-specific OTLP data satisfies the real E2E gate.
