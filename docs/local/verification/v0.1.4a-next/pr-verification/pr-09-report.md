## Scope delivered

Phase 1 adds a bounded Operations context. `internal/operations` owns versioned request/result models, typed handlers, registry, envelope validation, canonical request fingerprints, and execution dispatch. Read-only handlers reuse existing Health, Docker, and managed-dependency evidence. Phase 2 adds one opt-in Docker restart handler and an Operations infrastructure adapter while keeping discovery read-only. `internal/operations/sqlite` reuses migration v14 for execution state, append-only audit events, and transactional result outbox; uncertain restart results and crash recovery use its existing `UNKNOWN_OUTCOME` state. `internal/operations/nats` uses authenticated TLS JetStream pull consumption and PubAck-based outbox delivery. The test-only Mock Core provisions and consumes the scoped test messages. Optional Operations composition is isolated from telemetry lifecycle when broker configuration or service is unavailable.

The read-only operation types are `agent.diagnostics`, `container.inspect`, and `dependency.inspect`; `container.restart` is registered only when `AR_IMMS_OPERATIONS_CONTAINER_RESTART_ENABLED=true`. Its target also needs `ar-imms.operations.container-restart.enabled=true`. Requests bind target and parameter to one full 64-hex Docker ID; a fresh inspection requires that ID, opt-in label, and `running` state before the single restart call. Post-action evidence is the same ID with a strictly newer `StartedAt` or increased Docker restart count. Docker left `RestartCount=0` after a real manual restart on the verified Windows engine, while `StartedAt` advanced; the handler accepts that timestamp as evidence and reports recovery separately. It does not repeat the action on API uncertainty, timeout, duplicate delivery, or Agent crash. Those cases persist/replay `UNKNOWN` / `UNKNOWN_OUTCOME`. Container inspection remains an allowlisted projection and does not expose environment, labels, mounts, or raw Docker SDK data. A repeated operation ID with a different request fingerprint is rejected. The Operations runner acquires an installation-scoped process lock before startup recovery and command consumption. Handler execution is bounded to 30 seconds or request expiry, and ACK progress is extended while a handler runs.

Core remains the business authorization authority. `requested_by` and `authorization_ref` are retained as bounded audit correlations only. The Agent checks TLS broker scope, installation/binding identity, expiry, operation allowlist, and exact targets. These local contract files do not supersede or modify `docs/shared/` or provide production Core authorization.

## Historical preimplementation audit

The initial source audit at PR-08 merge `d1429196e8b39a24a624a9ad30619476f09a0a9f` found no published Operations dispatch or result contract. The [enrollment contract](https://github.com/AR-IMMS/shared-docs/blob/main/contracts/openapi/agent-enrollment.openapi.yaml) explicitly did not define control-plane operations, and the [Core API baseline](https://github.com/AR-IMMS/core-backend/blob/dev/api/baseline.yaml) had no API paths. The former readiness-only report marked PR-09 BLOCKED because no contract was then approved. This checkpoint proceeds with the user's approved Agent-local Phase 1 design; the findings remain relevant to production Core interoperability and do not authorize Core-side changes.

## Open decisions and follow-up

1. Track the production NestJS Core API and broker provisioning implementation separately. Do not block Agent Phase 1 on that integration; do not claim production interoperability until Core adopts the versioned binding and result contracts.
2. The Agent/Mock Core Phase 2 verification gates pass. Keep the handler disabled by default; approval of its policy does not constitute deployment opt-in.
3. Keep Windows and Linux evidence separate. Native Windows elevated restart evidence is from the implementation worktree before commit (with only formatting and an unused-test-helper removal afterward); final-head Windows CI ran all Go tests but skipped Docker-dependent live tests. Native Linux restart and final-head CI passed at `d2852be`.
4. Review result/audit retention bounds with Core's replay duration before release acceptance; the current implementation retains SQLite execution identity and uses bounded NATS stream retention configured by infrastructure.

## Files and rollback

Agent-local JSON schemas, transport contract, and ADR document the Phase 1 boundary. Local architecture and release-progress documents now identify the implemented context and current gate state. No `docs/shared/`, Core production code, collector behavior, or CLI surface is changed by this checkpoint. SQLite migration v14 is additive. Rollback is to stop provisioning Operations credentials and remove the optional runtime configuration; existing telemetry and lifecycle remain independent. A schema downgrade is not supported or required.
