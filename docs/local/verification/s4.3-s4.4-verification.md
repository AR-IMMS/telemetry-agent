## Live Redis flow and outcome distinction

1. The Agent Service used the local Docker Desktop engine and discovered the disposable Redis container into isolated SQLite inventory.
2. Matching produced a Redis proposal with endpoint `127.0.0.1:60779` and verified Windows artifact capability evidence.
3. The operator approved through the built `agentctl discovery proposals approve` command. The atomic approval result reported integration `discovered-060a1c6322340b9b2af4b66a`, instance revision 1 and desired-set revision 1.
4. The Agent Service's existing S3 controller observed desired revision 1 and applied it through S2/M2. The lifecycle reported generation 2 and the candidate digest above.
5. The active Collector config was read from the isolated root and checked for Redis receiver/pipeline membership plus preserved host telemetry components.
6. A separate isolated OTLP sink received Redis receiver scope and actual Redis data points. This establishes telemetry delivery, not merely Collector readiness.

**Applied**, **Collector ready**, and **telemetry delivered** are separate observations. This run established all three for Redis on Windows. PostgreSQL/Mongo verification established discovery/matching/proposal behavior only.

## Issues found and corrected

- The first full test attempt collided with a still-running isolated E2E Agent on the default status port. After stopping only the exact task-owned E2E processes and confirming listener cleanup, the full suite was rerun.
- Schema-version tests were stale after migration 12. Assertions were advanced to schema 12 while the direct migration-v10 test retained its v11 expectation. The populated-v9 test now removes migration-12 artifacts before exercising the upgrade to current schema.
- A `Put` no-op comparison treated an omitted legacy `Source` and explicit `local` as different intent. SQLite equality and snapshots now normalize the empty source to `local`; idempotent no-op tests pass without weakening the assertion.

## Acceptance limitations

- A fresh live `agentctl integration match` candidate was verified inside the opt-in Docker test; it proved no desired-state or M1/M2 mutation. Running the CLI later against expired evidence returned `stale`, as intended. The full live S4.4 workflow separately exercised matching via the Agent Service.
- The required failure matrix was not fully exercised against a live Collector: Redis restart/removal, endpoint change, daemon outage, Agent restart after approval, stale approval, double approval under runtime concurrency, and injected activation/readiness failure/LKG recovery remain unverified as live scenarios. Corresponding unit/persistence coverage exists for relevant proposal/approval invariants, but it does not substitute for those E2Es.
- Linux Go tests passed in a Linux container with the expected synthetic OS identity fixture. Linux Redis Agent/Collector delivery remains unverified; cross-platform capability evidence is not runtime delivery.
- CI and Draft PR validation passed on both supported CI operating systems. The remaining live failure/restart cases above are still unverified.
